# CreditLife-Agent 技术亮点

> 本文档面向想深入理解本项目设计的人：它是什么、为什么不是"单 Agent + prompt 变体"、每个关键设计解决什么问题。
> 配套阅读：[使用指南](使用指南.md)（怎么跑起来）、[架构图](架构图.md)（Mermaid 图）、[评测报告](评测报告.md)（真实数字）。

## 定位

CreditLife-Agent 是一个**覆盖信贷全生命周期的多 Agent 智能客服编排运行时**，而不是一个单纯的聊天机器人。

它把意图识别、知识检索、三层记忆、路由、工具治理、监控和评测串成一条闭环：系统先理解用户问题，再决定由哪个 Agent 主处理、是否需要其他 Agent 辅助、是否查知识库、是否升级人工，最后把结果写回记忆和观测系统。

选择信贷场景不是换皮：信用卡客服规则密集（息费、分期、征信），合规红线清晰；而贷后与催收是监管风暴眼（催收国标 GB/T 45251-2025、中银协催收指引），对抗场景真实且极端（诱导违规承诺、轻生威胁、第三人催收骚扰）。**一套系统覆盖两条高风险业务线，评测重点从"答得好不好"扩展到"答得合不合规、危机处理对不对"**。

核心形态：

```
意图识别 -> 路由决策 -> 单 Agent / 并行多 Agent 执行 -> 响应合并 -> 记忆回写 -> 监控/评测反馈
```

## 亮点一：三路融合意图识别

文件：`core/intent_recognizer.py`

**解决的问题**：客服路由最怕把"最低还款影响征信吗"误判成普通咨询，或把复合问题拆错。只靠关键词鲁棒性差；只靠 LLM 成本高、延迟高、行为不稳定。

**当前实现**：`recognize()` 并行启动 LLM（语义理解）和 Embedding（模板相似度），Pattern 规则同步执行，最后加权投票合并；LLM 权重最高，Pattern 负责零延迟兜底和细粒度纠偏，低于阈值回退 `other`。

输出不是单一分类标签，而是结构化结果：`intent`（18 类）、`intent_group`（归一化意图组）、`intent_confidence`、`intent_source_scores`、`urgency`、`entities`（卡号后四位/金额/日期/错误码规则抽取）。这让路由、升级、知识检索都能直接消费结构化信息。

**设计意义**：意图识别是后续路由、澄清、升级的结构化输入层。94 条分层评测集上，意图组级准确率 77.8%（信用卡线 93.3%），三路分数在 `/chat` 响应中全程可观测、可归因。

## 亮点二：路由驱动的多 Agent 编排 + 确定性危机干预

文件：`agents/agent_orchestrator.py`

**解决的问题**：多 Agent 的差异如果只在 prompt，就会出现"能力边界失控、复合问题强行塞给一个模型"。

**当前实现**：四类运行时角色——账单服务（billing）、技术支持（technical）、综合接待（general）、人工交接（escalation）——各有角色契约、工具白名单、输入输出边界和交接条件（`AgentProfile`）。路由不是选一个 Agent 就结束，而是生成结构化 `RoutingDecision`（primary_agent / supporting_agents / routing_reason / routing_confidence）；复合问题（如"App 登录报错 + 账单重复扣款"）由主 Agent 主处理、辅助 Agent 并行补充，再由 ResponseComposer 合并。

**危机干预是确定性代码，不依赖 LLM**：轻生/自伤类表述在路由决策最前置的位置被拦截，走固定分支——停止还款话题、共情安抚、提供心理援助热线（12356）、强制升级人工。这条分支不经过意图投票和 LLM 生成，保证最坏情况下行为确定。

**设计意义**：Agent 差异 = 契约 + 工具边界 + 路由位置；高危场景 = 确定性代码优先于生成式回复。

## 亮点三：双业务线 Skill 分流

文件：`core/skill_loader.py`、`skills/`

**解决的问题**：同一句"还款"，信用卡语境和贷后语境的合规话术完全不同（账单分期规则 vs 逾期协商边界），混用会互相污染。

**当前实现**：5 个可热加载的 SKILL.md——信用卡线（综合接待/账单服务/技术支持）+ 贷后线（逾期协商/催收投诉接待）——按"消息关键词 + Agent 类型"双条件匹配，关键词在两条业务线间严格切分（"逾期/协商"只命中贷后线，"分期/账单"只命中信用卡线），命中后注入对应 Agent 的 system prompt（上限 8000 字符防膨胀）。修改规则后 `POST /skills/reload` 热加载，不改代码主链路。

**设计意义**：业务规则（话术边界、禁止性表述、升级条件）独立于代码迭代，运营可维护；双线切分让一套系统服务两条风险特征完全不同的业务线。

## 亮点四：合规优先设计

文件：`skills/loan_billing_support/`（催收红线手册）、`evaluation/evaluator.py`、`agents/agent_orchestrator.py`

**解决的问题**：信贷客服最大的风险不是答错，而是**答得不合规**——承诺收益、承诺洗白征信、教用户以卡养卡、违规承诺减免。

**当前实现**：
- 催收红线手册按 GB/T 45251-2025 口径编写（催收时段限制、仅联系债务人本人、频次受限、禁止威胁恐吓），作为 RAG 语料 + Skill 规范双重注入；
- 绝对化表述与违规承诺拦截（"稳赚不赔""保证洗白征信""以卡养卡"类请求正确拒绝并给出合规路径）；
- 危机干预确定性分支（见亮点二）；
- **评测把"合规性"作为第五个独立维度**（0/0.5/1 红线量规），对抗用例 12 条全部正确拒绝，最终轮合规分 1.00。

**设计意义**：合规不是 prompt 里的一句话，而是"语料 + 规范 + 拦截分支 + 独立评测维度"四层兜底，且每一层可被评测量化。

## 亮点五：意图驱动的 RAG 与工具治理

文件：`api/main.py`、`mcp/tool_manager.py`、`mcp/knowledge_base.py`

**解决的问题**：不是所有问题都适合检索——寒暄、转人工不该查库；而业务问题必须"先检索后回答"，否则模型自由发挥就是合规风险。

**当前实现**：RAG 是 Agent 主动调用的工具（强制策略：业务事实先检索后回答），检索链路 = LLM 查询改写成多角度子查询 → 多子查询并行召回 ChromaDB → 合并去重 → LLM 重排 → Top-K 注入。知识库为 15 篇信贷业务语料（息费、分期、还款渠道、争议处理、催收红线、征信异议、冒名借款、法催调解）。

工具层治理：TTL 缓存（300s）、熔断器、fallback 降级、参数校验、调用链路 trace（`/trace/tools` 可查每次工具调用的输入输出与耗时）、**知识库更新即主动失效缓存**。

**设计意义**：检索不是"见词就搜"的噪声源，而是受意图约束、受工具层治理、可观测的受控能力。

## 亮点六：三层记忆体系

文件：`memory/conversation_memory.py`

**解决的问题**：客服对话既要记住当前轮，又不能把全部历史塞进 prompt，还要保留跨会话偏好——三种信息时间尺度不同，放一个窗口里会互相干扰。

**当前实现**：

| 层 | 存储 | 内容 | 策略 |
|----|------|------|------|
| 工作记忆 | Redis | 当前会话最近消息 | TTL 24h；达 15 条自动 LLM 压缩，保留最近 5 条 |
| 会话摘要 | Redis | 压缩摘要 | 同会话下次请求直接拼入 prompt |
| 情景记忆 | ChromaDB episodic | 摘要 + 元数据 | 跨会话语义检索相关历史 |
| 用户画像 | ChromaDB user_profile | 偏好和关键实体 | 每轮异步提炼 |

**设计意义**：控制上下文长度的同时保留跨会话连续性；Redis 异步客户端 + ChromaDB 线程池化，避免阻塞主请求链路。

## 亮点七：Monitor 在线观测与路由降权

文件：`monitor/performance_monitor.py`

**解决的问题**：多 Agent 系统不能只在设计时合理，还要在运行时保持健康——语义上最合适的 Agent 也可能因延迟升高、工具异常而不再适合接单。

**当前实现**：Monitor 定期采集 Agent 成功率/平均延迟、工具成功率/延迟/连续失败/熔断状态，做异常检测并生成告警与建议；结果写回 `monitor_penalty` 影响后续 `routing_score`。

**设计意义**：路由不是静态的——系统根据在线表现自动避开状态变差的节点，监控也不只是展示面板。

## 亮点八：LLM-as-Judge 端到端评测闭环（含合规维度）

文件：`evaluation/evaluator.py`、`data/eval/`

**解决的问题**：没有评测，优化只能靠感觉；通用评测又评不出信贷场景最关键的合规风险。

**当前实现**：
- **94 条分层评测集**：意图 54 条（信用卡 30 + 贷后 24，易/中/难三层）+ 对话 40 条（单轮/多轮/合规对抗/危机干预，12 条带 expected_behavior 行为断言）；
- LLM-as-Judge 五维评分（相关性/准确性/完整性/有用性/**合规性**），合规维度按 15 条红线量规打分；
- 回归检测（与基线对比输出 regressions）+ 优化建议；
- **三层校准**：双 Judge 交叉校准（独立 Judge 模型重评 20 条样本，合规维度一致率 100%）+ 20 条人工抽标（±0.25 容差下人机一致率 96%，人工比 Judge 更宽松 → Judge 保守不偏袒）+ 多轮基线回归（最终轮 0 退化）。

**设计意义**：项目从"能跑"变成"能量化迭代"——每一轮改动（路由修复、Pattern 词库修正、危机干预前置）都有前后数字支撑，且 Judge 本身被校准过，数字可信。

## 模块协作关系

```
api/main.py
├── /chat
│   ├── MemoryManager.get_context()          # Redis 工作记忆 + episodic + user_profile
│   ├── IntentRecognizer.recognize()         # 三路融合 → intent/group/confidence/entities
│   ├── AgentOrchestrator.run()              # 危机干预前置 → 结构化路由 → 主辅并行
│   │   └── Agent(工具白名单) → MCPToolManager → KnowledgeBase(RAG)
│   ├── MemoryManager.add_message()          # 写回 + 压缩
│   └── MemoryManager.update_profile()       # 异步画像
├── /skills  /skills/reload                  # SkillManager
├── /search                                  # 查询改写 → 召回 → 重排
├── /knowledge/add|upload|stats              # 知识库管理（更新即清缓存）
├── /monitor  /metrics                       # PerformanceMonitor / Prometheus
├── /trace/tool/{id}  /trace/tools           # 工具调用链路
└── /eval/run                                # EndToEndEvaluator（五维含合规）
```

## 数据存储设计

| Collection / 存储 | 写入来源 | 查询用途 |
|-------------------|---------|---------|
| ChromaDB `knowledge_base` | 15 篇信贷语料自动导入、/knowledge/add、/knowledge/upload | /search 与 /chat 的知识检索 |
| ChromaDB `episodic` | 工作记忆压缩后的摘要 | 跨会话语义检索历史 |
| ChromaDB `user_profile` | 每次 /chat 后异步更新 | 个性化与长期偏好 |
| Redis `wm:` / `summary:` | 每轮对话 | 当前会话上下文与摘要 |

## 一句话总结

CreditLife-Agent 把识别问题、路由角色、协作执行、检索知识、管理记忆、注入规范、监控质量、量化评测串成了闭环——并且把信贷场景最关键的**合规**做成了从语料、规范、拦截分支到独立评测维度的完整兜底。

它是一个可观测、可评测、可降级的双业务线多 Agent 客服运行时。
