# CreditLife-Agent 面试问答手册（AI 产品经理）

> 用法：面试前通读，重点背【口径红线】和【2 分钟叙事】；每条追问都给出了"标准答法 + 证据位置"。
> 埋点 = 提前在项目/文档里故意留的"钩子"，引面试官来问我们已经准备好的问题。

## 0. 口径红线（先背这个，说错任何一条都可能穿帮）

1. **项目来源口径**：说"从一个通用的电商客服多 Agent 架构出发做的信贷场景改编与深入"，**不要说"完全自己从零写的"**，也不要主动提上游项目的名字。被追问"架构是自己写的吗"→"核心编排框架来自一个开源社区项目，我做了信贷场景改编、合规评测体系设计、多项缺陷修复和迭代，改编工作量占大头，具体我可以指给你看"。
2. **数字口径**：只说真实测过的数字——意图准确率 90%（50 条版本）/【94 条三轮回填】、合规对抗 12 条（6 条催收红线）全部正确拒绝、回归 0 退化。没跑过的数字一个都不说。
3. **MCP 口径**：被问 MCP →"借用了 MCP 的思想做工具层治理（缓存/熔断/降级），没有接标准 MCP 协议，因为当前没有外部系统要对接；如果接真实业务接口，会按标准协议封装"。
4. **模型口径**：LLM 用通义千问 qwen-plus（百炼 Anthropic 兼容端点）；Judge 可独立配置（EVAL_JUDGE_MODEL）。
5. **缺口坦然承认**（见 Roadmap，全部是"我知道+有方案"的缺口，不是"不知道"）。

## 1. 两分钟项目叙事（开场必背）

"这个项目是一个覆盖信贷全生命周期的多 Agent 智能客服系统。它从电商客服架构改编而来，我做了两层深化：第一层改编到银行信用卡客服场景，规则密集、合规红线清晰；第二层深入到消费信贷的贷后和催收合规——这是监管风暴眼（催收国标 GB/T 45251-2025、中银协 2026 指引），对抗场景最真实。
架构上：意图识别用 LLM+向量+规则三路融合，路由到账单/技术/综合/人工四类 Agent，RAG 用查询改写+并行召回+LLM 重排，记忆分 Redis 工作记忆、情景记忆、用户画像三层。
我最有价值的两块工作：一是**合规评测体系**——LLM-as-Judge 我加了合规性维度，把催收红线写成 15 条可量化规则，配了 12 条对抗用例，包括轻生威胁、诱导骚扰第三人这种极端场景，系统全部正确处理；二是**评测驱动的迭代**——我通过评测发现知识库检索 0 触发，用对照实验定位到是工具引导策略缺失，修复后 RAG 正常工作，两轮回归 0 退化。整个过程中我还修了四个基础设施缺陷。"

## 2. 八大技术亮点话术（标准答法）

### 2.1 三路融合意图识别
"没有做成单一分类器：LLM 负责语义（权重 0.7），向量负责相似度匹配（0.2），规则负责零延迟兜底和高精度命中（0.1），加权投票后输出不只是 intent，还有意图组、置信度、各路来源分数、紧急度、结构化实体。**LLM 置信度越低，它的加权贡献越小，结果越往确定性规则的方向拉**——这就是三路融合的价值。"
追问"为什么 LLM 占 70% 不是 100%"→"LLM 输出不可控，另外两路是可控的；参数可调（可到 50/50），我调到当前组合后评测效果最好，就像调超参，调完就固定。"
追问"Embedding 是真的语义匹配吗"→**坦然**："当前是本地字符 n-gram 哈希相似度，不是真语义——这是个已知局限，Roadmap 里写了换中文语义向量模型；Pattern 那路是必要的，负责强特征兜底。"

### 2.2 路由驱动的多 Agent 编排
"路由是纯规则打分、无 LLM 介入——意图识别那一步已经用过一次 LLM，路由再调一次只会加延迟。意图类别、关键词、结构化实体、Agent 在线表现都会进打分。复合问题（登录报错+重复扣款）主辅 Agent 并行处理。"
**我们的修复**："原版辅助 Agent 用浮动门槛（分数≥主分×0.55），主 Agent 因关键词堆叠得高分时辅助永远进不来——我改成了固定门槛，并把复合领域检测（关键词+意图双信号）接进路由兜底。"

### 2.3 意图驱动的 RAG（重点，面试官必问）
"不是见词就搜：先意图判断，业务类问题才检索。检索链路是查询改写→多子查询并行召回→合并去重→LLM 重排→Top-K，工具层有 TTL 缓存、熔断器、fallback。"
**我们的修复故事（最硬的素材）**："评测时我发现知识库检索触发率是 0——模型在裸答。我做对照实验：同一批工具定义裸上下文调用会正常返回 tool_use，说明不是端点不支持，是提示层问题——工具描述没写使用策略，Agent 系统提示词又引导它直接回答。修复是工具描述加强制策略 + 系统提示词加通用工具策略，修复后 RAG 正常触发，评测耗时从 496s 涨到 608s（每轮多了检索往返，侧面证实）。"
追问"为什么不先意图门控再检索"→"门控依赖意图识别的准确率，误判会导致该搜不搜；现在的设计是把检索做成工具让 Agent 按策略自主决策，两者可以结合——比如意图组做强过滤、Agent 做最终决策。"
追问"怎么评估 RAG 质量"→"检索侧看触发率、Top-K 命中率、重排前后对比；生成侧靠 Judge 的 accuracy/completeness 维度+人工 badcase 归因（检索失败/意图误判/话术越界三类）。chunk 策略当前是 500 字定长切片，结构化分块是优化项。"

### 2.4 三层记忆
"Redis 工作记忆（最近 20 条，TTL 24h，达 15 条 LLM 压缩成摘要）、ChromaDB 情景记忆（跨会话语义检索）、用户画像（长期偏好）。分层的理由是时间尺度不同：当前轮是短期上下文、摘要是跨轮线索、画像是长期偏好，塞一个窗口会互相干扰。"
追问"压缩丢信息怎么办"→"两层防御：事前压缩前保留原文低成本存档可回溯；事后画像和摘要允许人工或规则纠正。这也是 Roadmap 里的完整对话记录持久化。"
追问"上下文容量"→"工作记忆只拼最近 5 条+摘要进 prompt；Skills 注入有 8000 字符上限防挤占；长上下文预算靠压缩和分层控制，不是无限堆。"

### 2.5 双业务线 Skill 体系（我们的原创增量）
"信用卡和贷后两套话术规范，按关键词精确切分注入，防止互相污染——比如'逾期'归贷后、'年费'归信用卡。代价是字符串包含匹配对口语化表达脆弱，Roadmap 里写了语义匹配兜底。"

### 2.6 合规评测维度（我们最大的差异化）
"LLM-as-Judge 我加了 compliance 维度，把红线写成 15 条可执行规则：不承诺收益、不承诺消除征信、不索要敏感信息、不威胁恐吓、不得向第三人催收、22 点到 8 点不催收（GB/T 45251-2025）……对抗用例 12 条带 expected_behavior 字段做定向评判。**催收红线对抗 6 条全部正确拒绝，包括轻生威胁——危机干预是确定性代码分支，不交给概率模型：停止还款话题、转介心理援助热线、强制人工。**"
追问"为什么危机处理用代码不用模型"→"安全关键路径要确定性：关键词命中就走固定流程，LLM 再好也不能把轻生场景交给概率。"

### 2.7 评测闭环与 Judge 校准（AI PM 核心卖点）
"评测集 94 条，意图三层（正例/变体/对抗）+ 对话（单轮/多轮/合规对抗），标注规范写了分层定义和验收口径，流程是 AI 辅助初标+人工复核——这也是行业通行做法。指标：意图 Accuracy/Macro-F1、Judge 五维、合规均分、回归检测。"
追问"Judge 和被测模型一样，不就是你夸你自己吗"→"对，这是我主动声明的局限。三件事解决：① Judge 模型可独立配置，我用更强的 qwen3-max 做了独立复评；② 双 Judge 一致性对比脚本，量化偏差；③ 20 条人工抽标算人机一致率。报告里所有数字都带局限声明。"
追问"评测集怎么保证质量"→"AI 生成+人工抽检，抽检不合格率超阈值就改生成策略——和业界做法一致。"

### 2.8 监控与降权
"Monitor 定期采集成功率/延迟，写回 penalty 影响路由。诚实说：当前每类 Agent 单实例，penalty 实际影响'同类型多实例选哪个'，单实例下不生效——这是为水平扩展预留的设计。多实例不同模型还有成本意义：低价模型能答就不触发高价模型。"

## 3. 高频追问预案（问答区 60 条精选 + 面经）

| 追问 | 标准答法 |
|------|---------|
| 为什么不用 LangGraph？ | 框架封装重；不用框架链路更透明，查询改写/重排/降级都能自己控制；学习目的下自己维护工程细节更有价值 |
| 为什么选 ChromaDB 不是 Milvus/ES？ | 数据量级（个人项目、几万片段）用不到分布式；ChromaDB 内置 embedding、零运维；数据量大后可平滑换 |
| 意图层和路由层都有关键词判断，冗余吗？ | 不冗余：意图层的关键词参与"决出唯一主意图"，投完票证据就丢了；路由层的关键词是对原始消息的独立二次扫描，专门找回被取舍掉的次要信号（复合问题双保险） |
| 工具没接真实业务接口怎么说？ | 演示环境无真实业务系统；工具层已抽象好（白名单+Schema 校验+治理），接真实接口只需实现 handler——接口是现成的 |
| 延迟多少？ | 实测端到端约 5-10s（qwen-plus，含工具往返）；评测 94 条一轮约 20 分钟；优化方向是缓存命中、小模型分流 |
| Agent 回复口径冲突怎么办？ | 多 Agent 结果交给 Composer 以主 Agent 结论为主轴合并；冲突时不选边、提示需核验；无硬性冲突检测是已知局限 |
| 这个项目最难的地方？ | 不是写代码，是**发现问题**：RAG 0 触发、ChromaDB where 格式错、浮动门槛 bug，全靠评测和对照实验定位——评测体系是发现的眼睛 |
| 你是 PM，为什么要写代码？ | 我不写核心算法，但我必须能读代码级深度：评测归因要能下钻到提示层和工具层；这个项目里我定位的四个缺陷没有代码级阅读能力一个都发现不了 |
| 2026 新概念（Context Engineering / Harness）了解吗？ | 上下文工程本质就是我做的事：三层记忆+压缩+Skills 注入上限+检索按需触发，都是在管理有限上下文的预算；Agent Harness 是运行时治理——我的工具熔断/降权/评测回归就是 Harness 思维 |

## 5. 面经来源与新增考点（2026 秋招）

- 评测集设计能力是 AI PM 面试核心考察点；RAG 效果取决于解析/分块/Embedding/检索策略每个环节——对应我们的 chunk 优化项和 embedding 局限声明
- 字节系 Agent 面重点：模型输出接业务、**上下文预算**、**工具越权与副作用控制**——对应我们的工具白名单、TTL 缓存、熔断降级
- 系统设计高频：RAG + 多 Agent 架构；追问集中在召回率评估、chunk 策略、知识库更新一致性（我们已做缓存失效）
- 新题型：概念认知题（Context Engineering 等），答法见 3.8
